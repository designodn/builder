# /test

Тестовый прогон проекта. В quick-режиме считает статические метрики. В `--full`-режиме — автономно проигрывает полный пайплайн `/builder` от лица **случайного сениор-дизайнера**, собирая бэклог доработок до раскатки продукта.

## Жёсткие границы (нельзя обходить)

1. **Запускать `/test` может только Настя.** Перед любым шагом — identity-check как в `CLAUDE.md` шаге 1. Если ответ «нет» — стоп с сообщением: «Тесты запускает только Настя. Если хочешь, можем запустить `/builder`».
2. **Никаких правок кода, правил, реестра, агентов или конфигов.** `/test` только читает и записывает в `tests/`, `docs/COMPONENT_RULES_ISSUES.md` и `tests/metrics.jsonl`. В `--full` дополнительно создаёт **новую** страницу `test N` в файле `twL50t4GFELOKpEwFWSvwW` через `use_figma`. Никогда не трогает существующие страницы Figma и другие файлы. Найденные проблемы идут в журнал, не в код.
3. **Запись в журналы:**
   - В **quick**-режиме — после явного апрува Насти на каждый блок (показать что записать, дождаться «да»/«ок»).
   - В **`--full`**-режиме — issues записываются автоматически по ходу adversarial-прогона (без вопросов): это часть теста, артефакт сборки бэклога.
4. **Append в `tests/metrics.jsonl`** — артефакт замера, пишем без апрува (но никогда не перезаписываем существующие строки).
5. **Коммит** — только по явному «коммить» от Насти. Push — никогда без отдельного запроса.

## Режимы

| Флаг | Что делает |
|---|---|
| `/test` | Только статика: реестр, правила, размеры контекста. Без `use_figma` и без пробного `/builder`. |
| `/test --full` | Статика + полный adversarial-прогон `/builder`: случайная персона дизайнера, случайная задача, споры по ходу, сборка макета в Figma, пакет правок в конце. Цель — собрать бэклог доработок. |
| `/test --component <name>` | Микро-тест одного компонента: createInstance → 9 ассертов (bounds, children, paired-aware placeholder check, text/swap/variant mutability, PNG visual diff). Один `use_figma`-вызов, ~3-5k токенов. **Используется оркестратором `/parseProps` как sub-skill.** |
| `/test --component <name> --matrix` | То же, но прогон по всем вариантам компонент-сета (до 12). |

По умолчанию — quick. Полный режим запускается явно, потому что тратит токены и время Figma.

## Алгоритм

### Шаг 0 — Стартовый снимок верификатора

**Обязательно** до любых других шагов выполни процедуру `V-START` из `.claude/commands/verifier.md`. Цель — зафиксировать стартовые числа из файлов, чтобы в финальном отчёте сверяться с ними, а не с памятью агента.

```bash
echo "## Стартовый снимок $(date -Iseconds)"
echo "metrics.jsonl: $(wc -l < tests/metrics.jsonl) строк"
echo "heal-log.jsonl: $(wc -l < tests/heal-log.jsonl 2>/dev/null || echo 0) строк"
echo "components: $(jq '.components | length' registry/index.json)"
echo "approved: $(jq '[.components[] | select(.[4] == true)] | length' registry/index.json)"
```

В `--full`-режиме после каждых 10 экранов прогона — `V-CHECKPOINT`. Финальный отчёт строится через `V-FINAL` (все числа из файлов в момент вывода, не из памяти).

### Шаг 1 — Статические метрики

Запусти:

```bash
node tests/scripts/static-metrics.js
```

Скрипт читает реестр и правила, печатает JSON. Дальше используй этот JSON для шагов 2–5. Если нужно поменять логику замера — правь `tests/scripts/static-metrics.js`, не этот файл.

### Шаг 2 — Прочитать прошлые запуски и посчитать дельту

Прочитай `tests/metrics.jsonl`. Это JSONL — каждая строка независимый JSON. Возьми **последнюю** строку как `prev`. Если файла нет или строк меньше двух — считается, что прошлых запусков нет, дельты пропускай.

Также прочитай предпоследнюю строку как `prevPrev` для тренда (стрелки вниз/вверх).

### Шаг 3 — Если режим `--full`, дополнительно

#### 3a. Adversarial `/builder` — автономный прогон с двумя ролями

Прогоняешь **весь** `/builder` от начала до готового макета (включая шаг 7 — Figma write). Без `AskUserQuestion`. Играешь две роли по очереди: **«дизайнер»** и **«билдер»**. Цель — найти дыры в правилах, реестре и агентах.

**Принимаемый дрейф.** Этот скилл намеренно **не** синхронизируется автоматически с `.claude/commands/builder.md` через registry/extractor (см. закрытый PR 226 — попытка broker'а оказалась дороже выгоды: каждое добавление якоря в builder требует регенерации, CI drift-detector, кэш-инвалидаций; при этом adversarial-прогон от формальной точности списка гейтов не выигрывает). Если builder.md обновился — отступления test.md от него допустимы, пока шаги 7.5 (визуал) и 7.6 (программный аудит) ловят реальные регрессы в Figma-сборке. Объективные находки идут через эти два шага + шаг 7.7 (аудит `_session.*`), субъективные текстовые расхождения — не баг.

**Шаг 0 — Сгенерируй персону дизайнера.** Случайно (каждый прогон — новая персона):

| Параметр | Варианты |
|---|---|
| Знакомство с ДС | (a) опытный — знает правила, соглашается с компонентами по умолчанию; (b) зелёный — путается, пушит «нестандартные» решения, спорит |
| Размер задачи | **small** (≤ 5 экранов) / **medium** (≤ 15 экранов) / **large** (> 15 экранов) |
| Сложность | simple (форма, статика) / mixed (форма + список) / complex (флоу со ветвлениями) |
| Особенность | без / странные метрики («хочу чтобы CTR вырос — добавь ярких баннеров») / противоречивые требования / просьба сделать «как в проде у X» без референса |

**Шаг 0.5 — Маркер adversarial-сессии.** Установи `_session.auto_mode = true` в начале прогона. Когда дойдёшь до Шага 8 builder.md (эмит telemetry-issue), убедись что в JSON-блоке `"auto_mode": true` (а не литерал `false` из шаблона) — иначе фильтр в `tools/aggregate-sessions.py` сработает на нуле записей и synthetic-прогон попадёт в A-056 leaderboard как живая сессия. Поле документировано в builder.md рядом с шаблоном telemetry-body.

**Шаг 1 — Дизайнер ставит задачу.** Сформулируй промпт от лица персоны (короткий и в её стиле). Запиши промпт.

**Шаги 2-6 — `/builder` отрабатывает.**

- **Research Agent:** дизайнер отвечает на вопросы. Опытный — кратко и по делу. Зелёный — иногда противоречиво, может настаивать на странном.
- **Расширения:** опытный — обычно пропускает. Зелёный — может выбрать всех «потому что круто».
- **CJM:** билдер строит, дизайнер (если зелёный) челленджит — иногда обоснованно, иногда нет. Билдер **критически думает**: если требование нарушает правила ДС или скелета — объясняет почему и предлагает компромисс. Если разумно — адаптирует.
- **Шаг 6 — план:** если в плане компонент без секции правил, используй `figma.importComponentByKeyAsync(key)` с дефолтами. **Каждый такой случай → запись в issues** (`agents` или `rules`).

**Шаг 7 — Figma.** Собери макет в файле `twL50t4GFELOKpEwFWSvwW`, всегда новая страница `test N` (N — следующий свободный номер).

**Шаг 7.5 — Визуальное ревью каждого экрана.**

| Что проверить | Признак бага |
|---|---|
| `meshok ↓` на абсолютной позиции, прибит к низу | Между контентом и meshok ↓ пустое пространство, или meshok ↓ уехал за границу фрейма |
| Лишние инстансы вне фреймов | Компоненты «парят» на странице рядом с фреймами (часто — при ошибке INSTANCE_SWAP, см. A-024) |
| Все навбары/таббары на месте | Заголовки экранов пустые, нет ни одного элемента в `meshok ↑` |
| Текст пропов выставлен | header/button с дефолтными плейсхолдерами вместо заданных строк |
| Скелет фрейма соблюдён | Отсутствует `meshok ↓`, кнопки прямо во фрейме, и т.п. |
| Размер фрейма правильный | Фрейм очень маленький/большой относительно стандартного 390×844 |

Для каждого замеченного бага — запись в `tests/issues/agents.md` (`A-NNN`) с пометкой «замечено визуально через get_screenshot».

Затем для **каждого фрейма по отдельности** вызови `get_screenshot` с его `id`. Никакого «одного общего скрина страницы» — только поштучно, иначе мелкие косяки не видны.

Смотри каждый скриншот как дизайнер-ревьюер: задача — увидеть «настоящий экран приложения», а не угадывать состояние по метрикам. По каждому кадру пройди все 10 пунктов:

| # | Что проверить | Признак бага |
|---|---|---|
| 1 | **Заголовок навбара** | Виден текст «Title», «Заголовок», «text» — navbar title не задан через setDeep |
| 2 | **Текст кнопок** | «label», «Кнопка», «Button» вместо реального текста — buttonsView label не задан |
| 3 | **Поиск и инпуты** | Поле пустое или с дефолтным hint — mask/hint prop не задан |
| 4 | **Ячейки / список** | Все ячейки одинаковые или текст = «Text» / «Описание» — данные не разведены через setDeep |
| 5 | **Баннеры / карточки** | Заголовок = плейсхолдер; изображение — серый прямоугольник; подзаголовок = «subtitle» |
| 6 | **Overlap meshok ↑** | Верхний мешок занимает > ~30% высоты экрана и перекрывает первые ячейки контента |
| 7 | **Orphan-компоненты** | Компоненты «парят» за рамкой фрейма — признак ошибки INSTANCE_SWAP |
| 8 | **Meshok ↓ прибит к низу** | Большой зазор между контентом и нижним мешком, или мешок вышел за нижний край |
| 9 | **Vibe / иконки / эмоция** | Все vibe/emotion одинаковые или neutral — контекст не задан |
| 10 | **Общий вид** | Экран выглядит как каркас-заглушка, а не приложение — слишком много серого/пустоты |

По каждому фрейму **обязательно** выведи строку:

```
[screen N · <Название>] ✅ ок
[screen N · <Название>] ⚠️ п.2 кнопки «label», п.4 ячейки одинаковые, п.6 meshok↑ перекрывает
```

Не пропускай ни одного фрейма. Каждая найденная проблема → `A-NNN` в `tests/issues/agents.md` («замечено визуально»).

**Шаг 7.6 — Программная проверка точности.** Сразу после визуального ревью прогони через `use_figma` plugin-код из `tests/scripts/full-accuracy.figma.js` по странице `test N`. Перед запуском в скоупе должна быть переменная `page` — страница `test N`. Скрипт возвращает объект:

```
{
  componentsRendered,
  placeholderHits,
  skeletonViolations,
  placeholderSignal,
  tokenCoverage: { paddings, fills, texts }
}
```

- `placeholderHits` — TEXT-ноды, всё ещё показывающие DS-плейсхолдер («Title», «Заголовок», «text»). Включает navbar middle title и любые другие TEXT-копи. **Целевое значение = 0.**
- `skeletonViolations` — нарушения скелета: meshok ↓ отсутствует или не абсолют, hardcoded paddings во фреймах builder'а, INSTANCE-ноды на уровне страницы (orphans). **Целевое значение ≤ 1.**
- `placeholderSignal` — сигнальная метрика «забытый swap»: wrapper-инстансы с `placeholder` mainComponent + INSTANCE_SWAP-пропы прямых детей фрейма с дефолтом `'12:6'`. **Не zero-target** (optional слоты тоже считаются), но рост означает регрессию.
- `tokenCoverage.{paddings,fills,texts}` — доля привязок к переменным ДС (0..1, выше = лучше). Только для нод, созданных Builder'ом (вне INSTANCE).

Если меняешь набор проверок — правь `tests/scripts/full-accuracy.figma.js`, не этот файл.

`totalPlanned` берётся из плана шага 6 (число INSTANCE-нод в плане). Считай:
- `componentCoverage = componentsRendered / totalPlanned` (1.0 = идеально)

**Шаг 7.7 — Аудит `_session.*` телеметрии.** После Figma write прочитай телеметрию сессии и сверь два источника. **Реестра гейтов нет** (он бы дрейфовал с builder.md быстрее, чем приносил пользу) — читаем только то, что Builder уже пишет в `_session` независимо от test.md:

- **`_session.rule_contributions[]`** — каждый элемент с `type: "structural-gap"` (компонент без guidance, builder выбирал без правила) → `R-NNN` в `docs/COMPONENT_RULES_ISSUES.md`. Каждый `divergence_step` отличный от `"ok"` (полный enum в builder.md: `"forgotten_text"`, `"unknown"`, `"role_no_match"`, `"unresolved_gap"`, `"unresolvable_force"`) → `R-NNN` или `A-NNN` в зависимости от природы (правило отсутствует vs builder не использовал имеющееся). Если массив `null` (а не `[]`) — обработай как пустой, не падай.
- **`_session.builder_picks[]`** с `confidence: "low-fallback"` — если такой pick привёл к визуальному багу из Шага 7.5 → `A-NNN` (builder мог переспросить, но решил сам). Если pick был ок (визуал чистый) — телеметрический сигнал, в issues не идёт.

Если поле в `_session` отсутствует — это просто означает, что Builder в этом прогоне не дошёл до соответствующего этапа. Не падай и не записывай это как fail.

**Шаг 8 — Дизайнер просит правки.** После сборки дизайнер задаёт **2-3 правки**. Постарайся, чтобы среди них были разные классы:
- одна реализуемая прямо сейчас (заменить текст, поменять компонент на другой из реестра, изменить вариант сета);
- одна требующая доработки проекта (нет правил для нужного компонента, или нужен новый prop в правилах, или нет шаблона под это);
- одна нереализуемая в принципе (нужен компонент, которого нет в ДС; платформенный паттерн не покрыт).

Билдер по каждой правке решает: **«делаю» / «пока не могу — нужно X» / «нельзя — нет в ДС»**. Те, что не делаются, идут в issues.

**Шаг 9 — Сводка прогона.** В `notes` строки `metrics.jsonl` и в текстовом отчёте обязательно:

```
## Прогон <ts>

**Персона:** опытный/зелёный, любит/не любит ДС, особенность=<X>
**Задача:** <короткое описание промпта>
**Флоу:** <итоговая последовательность экранов>

**Адаптации в споре:** <чего согласился изменить vs что отстоял>
**Правки в конце:** <3 пункта со статусом доделать/в бэклог/нельзя>

- R-NNN · <правило, которого не хватило>

Замеряй: `buildSampleSeconds` — **только время сборки в Figma** (от первого `use_figma`-вызова до завершения шага 7). Брифинг, ресёрч, CJM и план в это время не входят. `buildSampleTokensIn`/`CacheRead` — если доступны.


### Шаг 4 — Показать таблицу метрик с динамикой

Формат строго такой:

```
## /test · <режим> · <ts>

| Метрика | Сейчас | Прошлый | Δ | Тренд | Цель |
|---|---|---|---|---|---|
| rulesCoveragePct | 20.9% | 20.9% | 0 | → | ≥ 80% |
| propsDescribedCoveragePct | 18.3% | 18.3% | 0 | → | ≥ 80% |
| alwaysLoadedTokensEst | 8931 | 8931 | 0 | → | ≤ 5000 |
| buildSampleTokensIn | — | — | — | — | ≤ 8000 |
```

Колонки:
- **Сейчас** — значение из шага 1.
- **Прошлый** — из `prev` (последняя строка `metrics.jsonl` ДО текущего запуска).
- **Δ** — численная разница, со знаком.
- **Тренд** — `↑` улучшение, `↓` ухудшение, `→` без изменений. Учитывай, что для одних метрик «больше = лучше» (`rulesCoveragePct`, `propsDescribedCoveragePct`), для других — «меньше = лучше» (`alwaysLoadedTokensEst`, `buildSampleSeconds`, `buildSampleTokensIn`).
- **Цель** — из `tests/README.md` блока «Целевые ориентиры». Если метрика хуже цели — добавь `🔴`, если в норме — `🟢`, на грани — `🟡`.

**Граница рерайта static-metrics (2026-05-24, PR #238).** Определения `rulesCoveragePct` и `propsDescribedCoveragePct` пересмотрены: старая логика грепала `.md` (удалены в Phase 4), новая — `.rule.json` + полная семантика guidance (whenToUse / edgeCases / preferred[].usage). Прошлый snapshot до этого ts в `metrics.jsonl` несравним — при выводе Δ через эту границу пометь Δ как `n/a` и тренд как `→`, не делай выводов о регрессии/улучшении.

После таблицы — **раздел «Динамика»** с трендом по последним 5 запускам:

```
## Динамика (последние 5)

rulesCoveragePct:    4.8 → 4.8 → 4.8 → ... → текущее
alwaysLoadedTokensEst: 6884 → ... → текущее
buildSampleTokensIn (если был --full): ...
```

Если запусков меньше 5 — показывай столько, сколько есть.

### Шаг 5 — Записать issues

**В `--full`-режиме** issues собираются автоматически по ходу шага 3a (gap в правилах, галлюцинации билдера, нереализуемые правки, аудит `_session.*` из шага 7.7). Никаких вопросов Насте.

**В quick-режиме** этот шаг пропускается. Quick — это только замер метрик. Если по дороге что-то заметила — заведи через `/fb` отдельным заходом.

Формат записи issue (для `--full`):
1. Открой соответствующий журнал (`tests/issues/<cat>.md` или `docs/COMPONENT_RULES_ISSUES.md` для rules).
2. Найди следующий свободный ID (`C-NNN`, `O-NNN`, `A-NNN`, `R-NNN`).
3. Добавь новую запись в раздел «Открытые» с тогглом `[ ]`. Формат:
   ```
   ### [ ] X-NNN · <короткое имя>

   <описание проблемы>

   **Где:** <файл:строка если знаешь>
   **Как лечить:** <предложение>
   **Замечено:** /test <ts>
   ```

Возьми объект из шага 1, при `--full` добавь поля из 3a, обнови `notes` если уместно. **Append** (одна новая строка), **не перезаписывай** файл.

### Шаг 7 — Финал

Покажи Насте:

1. **Сводку прогона** (только `--full`): персона, задача, флоу, адаптации в споре, правки и их статус. Формат — из шага 9 в 3a.
2. **Таблицу метрик** из шага 4.
3. **Точность относительно прошлого прогона** (только `--full`, **всегда** отдельным заголовком — даже если показатели одинаковые):

   ```
   ## Точность макетов (vs прошлый --full)

   | Метрика | Сейчас | Прошлый | Δ | Цель |
   |---|---|---|---|---|
   | componentCoverage | 0.95 | 0.80 | +0.15 ↑ | ≥ 0.95 |
   | placeholderHits | 0 | 3 | -3 ↑ | = 0 |

## Режим `--component <name>`

Микро-тест одного компонента. Sub-skill для `/parseProps` и других оркестраторов. Не пишет в `metrics.jsonl`, не создаёт страниц в Figma. Стоимость — один `use_figma`-вызов (≈ 3–5k токенов).

### Жёсткие границы

1. Только Настя (identity-check как в шапке файла).
2. Никаких правок репозитория. Скрипт может писать только в `tests/heal-log.jsonl` (append) — никуда больше.
3. Никаких страниц в Figma. Создаётся временный `__heal_sandbox__`-фрейм в корне файла `twL50t4GFELOKpEwFWSvwW`. После микротеста sandbox **сохраняется** для визуального sanity-check (`get_screenshot(sandbox.id)`), затем удаляется отдельным cleanup-вызовом (`heal-cleanup-sandbox.js`).

### Алгоритм (агент исполняет шаг за шагом)

**Шаг 1. Pre-flight.** Чисто локально, 0 MCP.

```bash
node tests/scripts/parseProps-preflight.js "<name>"
```

Если `decision != "readyForMicrotest"` — НЕ запускай microtest. Выдай эскалации Насте:
- `resolveProps` → `/syncKeys --rescan --component='<name>'`
- `stubRule` → `node tests/scripts/parseProps-stub.js "<name>"` (создаёт rule.json + авто-genIndex)
- `needsRegistry` → search_design_system + `parseProps-stub.js` (см. preflight escalations)
- `scopedSync` → `/syncKeys --scoped --page=<X>`
- `fullBootstrap` → последовательно: rescan → stub
- `hypothesizePreferredUsage` / `hypothesizeDescription` → `/parseProps --hypothesize '<name>'`
- `abort:invalidApproval` (R-049: exit 3) → ручная починка: `set approved=false` в `rule.json` ИЛИ `/parseProps --hypothesize '<name>'` (заполнить usage для preferred), потом снова поднять `approved=true`.

**Шаг 2. Codegen.** Локально, 0 MCP.

```bash
node tests/scripts/parseProps-microtest.js "<name>"           # default variant
node tests/scripts/parseProps-microtest.js "<name>" --matrix  # full matrix (≤ 12)
```

Выдаёт JSON `{plugin, expected, meta}`. `plugin` — строка JS-кода. Учитывает из `rules/components/<slug>.rule.json`:
- `booleans[].pairedSlot` (1:1 boolean↔swap для pair-aware placeholder check)
- `layoutRules.layoutPositioning='ABSOLUTE'` → sandbox с `layoutMode='NONE'`
- `slots[X].preferred[]` — curated preferred keys с validated/broken/usage
- 1:N паттерны (button addons → 4 size-slots) покрываются runtime `rootName-fallback`
  в плагине, не из rule. См. контракт в `parseProps-microtest.js:ruleAsIndexEntry`.

**Шаг 3. Execute.** Один `use_figma`-вызов.

```
use_figma({
  fileKey: "twL50t4GFELOKpEwFWSvwW",
  code: <plugin string>,
  description: "/test --component <name>"
})
```

Плагин возвращает результат через `throw new Error("HEAL_RESULT:" + JSON.stringify(out))` — `console.log` из use_figma не возвращается, throw — единственный канал.

**Шаг 4. Parse.** Локально из ответа:

```bash
# Из error message use_figma:
node tests/scripts/heal-parse-result.js --text="<error_text>" | jq '.summary'
```

Парсер режет всё до `HEAL_RESULT:` и обрезает stacktrace.

**Шаг 5. Append лог + краткий отчёт Насте.**

```bash
echo "{\"ts\":\"$(date -Iseconds)\",\"component\":\"<name>\",\"summary\":$SUMMARY}" >> tests/heal-log.jsonl
```

Финальный вывод Насте (фиксированный формат):

```
## /test --component <name> · <ts>

| assert | result |
|---|---|
| instanceCreated   | ✅ / ❌ |
| variantApplied    | ✅ / ❌ |
| defaultsAcceptable| ✅ / ❌ + visiblePlaceholders[] |
| noPlaceholderText | ✅ / ❌ + samples |
| boundsNonZero     | ✅ + WxH |
| hasChildren       | ✅ + count |
| textMutable       | ✅ / ⏭️ skip / ❌ |
| swapMutable       | ✅ / ⏭️ skip / ❌ |
| variantMutable    | ✅ / ⏭️ skip / ❌ |
| visualDiff        | ✅ / ⏭️ skip / ❌ + bytes baseline→mutated |

**Verdict:** pass / autofix / needs_human / stuck
**Tokens (use_figma):** ~X k
```

### 9 ассертов — что проверяет каждый

| Ассерт | Что |
|---|---|
| `instanceCreated` | `main.createInstance()` без exception |
| `variantApplied` | `setProperties(defaultVariants)` без exception |
| `defaultsAcceptable` | Нет VISIBLE INSTANCE_SWAP с дефолтом `'12:6'`. Pair-aware: если master boolean = false → invisible, не считается |
| `noPlaceholderText` | Нет TEXT-нод с содержимым ∈ {Title, Заголовок, text, label, Button, Кнопка, subtitle, Описание} |
| `boundsNonZero` | `inst.width > 0 && inst.height > 0` |
| `hasChildren` | `inst.children.length > 0` |
| `textMutable` | TEXT-проп ставится на случайный `HEAL_TEST_<rand>`, читается обратно равным |
| `swapMutable` | INSTANCE_SWAP с preferredKey меняется, `componentProperties[prop].value` обновляется |
| `variantMutable` | VARIANT-проп переключается на non-default option, читается обратно |
| `visualDiff` | PNG bytes до и после mutation отличаются (mutation действительно повлияла на рендер) |

`skip` появляется, когда у компонента нет соответствующего пропа (например, у атома без TEXT — `textMutable: skip`).

### Кому полезно

- `/parseProps <X>` — после pre-flight'а зовёт `/test --component <X>`, скармливает результат в classifier
- `/parseSweep` — батч-режим (ранее `/healSweep`), вызывает на каждом компоненте scope'а
- Настя — для ручного дебага одного компонента: «что не так с meshok ↓»

## Что не делает `/test`

- Не закрывает issues автоматически. Закрытие — отдельная ручная процедура (см. `tests/README.md` про тоггл).
- В `--full` строит макет в Figma — но **только** на новой странице `test N` файла `twL50t4GFELOKpEwFWSvwW`. Никогда не трогает существующие страницы и другие файлы.
- Не правит реестр.
- Не вызывает `whoami` или MCP в quick-режиме (статика этого не требует).
