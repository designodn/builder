# /fb — зафиксировать баг или замечание

Создаёт GitHub issue с описанием проблемы и автоматически собранным контекстом. Доступен **всем** — и Дизайнеру, и Насте. Дизайнерам это основной способ сообщить о проблеме, потому что у них нет прав на edit/push.

## Куда пишутся issues

- **owner:** `kotik-botik`
- **repo:** `kotik-botik`

## Режимы

`/fb` поддерживает два режима, различающихся по аргументам:

1. **Обычный (баг/UX)** — без префикса или с префиксом `bug:*`/`feedback:*`. Описано в Шагах 1-5 ниже.
2. **Agent feedback** — аргумент начинается с `agent:<role>`, где `role` ∈ `research` / `analytics` / `product` / `experience` / `implementer`. Описано в разделе «Agent feedback» в конце. Использует другой набор вопросов и категоризации.

Если первый токен `$ARGUMENTS` равен `agent:<role>` (или просто `agent` — тогда спроси у дизайнера, на какого) — переходи в раздел «Agent feedback». Иначе — в Шаг 1.

## Шаг 1 — Есть ли описание

Аргументы команды: `$ARGUMENTS`.

Если пусто — спроси:

> «Расскажи, что пошло не так. Можно коротко: что делал, что ожидал, что получил. Если есть скриншот или ссылка на Figma — приложи.»

При односложном ответе задай 2-3 уточняющих вопроса.

## Шаг 2 — Собрать контекст автоматически

Не задавай эти вопросы дизайнеру — сам достань из сессии и файлов:

- **Этап `/builder`**, на котором был дизайнер (из истории сессии).
- **Имя упомянутого компонента** → проверь в реестре: `grep -F '"<имя>"' registry/index.json`. Запиши: есть в реестре / нет.
- **Связанное правило** → `slug = slugify(имя)` (см. `rules/components/ARCHITECTURE.md`), проверь `rules/components/<slug>.rule.json` — существует ли, `approved: true/false`.
- **HEAD:** `git rev-parse --short HEAD`.
- **Последняя ошибка Figma MCP** (если была в ответе `use_figma` в этой сессии).
- **Время:** ISO timestamp.

## Шаг 3 — Категоризация

Подбери одну категорию-label. Лейбл `designer-feedback` добавляется **всегда**.

| Label | Когда |
|---|---|
| `bug:registry-stale` | Компонент должен быть, но в реестре нет (или устаревший ключ). Дизайнер может попробовать `/update`. |
| `bug:missing-rule` | Нет `.rule.json` для существующего компонента. `approved: false` — НЕ баг, это WIP. |
| `bug:import-failed` | Figma вернула ошибку при импорте (404, key not found). |
| `bug:builder-error` | Странное поведение агента, не описывается другими категориями. |
| `bug:rule-incorrect` | Правило привело к плохому макету (неправильный вариант, не тот слот). |
| `feedback:ux` | Общее замечание по флоу `/builder` (запутался, не понял шаг). |
| `feedback:component-request` | Нужен новый компонент в библиотеку. |

Если непонятно — `feedback:ux`.

## Шаг 4 — Создать issue

Вызови `mcp__github__issue_write`:

```
operation: "create"
owner: "kotik-botik"
repo: "kotik-botik"
title: "[designer] " + краткая суть (≤80 символов)
body: markdown по структуре ниже
labels: ["designer-feedback", "<category>"]
```

### Структура body

```markdown
## Что я делал
<рассказ дизайнера>

## Что ожидал
<если выяснил>

## Что получилось
<если выяснил>

## Контекст (заполнено автоматически)
- Этап /builder: <шаг>
- Компонент: <имя или —>
- В реестре: <да/нет/—>
- Правило: <slug.rule.json: есть и approved / есть WIP / нет / —>
- HEAD: <короткий хеш>
- Последняя ошибка Figma: <текст или —>
- Время: <ISO>

## Скриншот / ссылка на Figma
<если приложил>
```

## Шаг 5 — Отчитаться

После успешного создания:

> «Зафиксировано: <URL issue>. Спасибо, Настя посмотрит.»

При ошибке создания (нет прав, MCP недоступен, неправильный owner/repo):

> «Не получилось создать issue автоматически — что-то с правами или сервером. Скопируй текст ниже и отправь Насте в Telegram.»

Выведи готовый markdown-блок.

**Не пытайся** записать issue в локальный файл репо — у Дизайнера Read-роль, push всё равно не пройдёт.

## Тонкости

- На уровне Настя — скилл тоже работает, но обычно Настя использует `tests/issues/*.md` через `/test --full` для системных багов. `/fb` — для разовых случаев.
- Если дизайнер сообщает о нескольких разных проблемах за раз — создай несколько issues, не сваливай в один.
- Не показывай дизайнеру JSON, `componentKey`, стектрейсы.

## Agent feedback (режим `agent:<role>`)

Отдельный поток для оценки работы конкретного эксперта в `/builder`. Запускается двумя способами:

1. Дизайнер сам пишет `/fb agent:analytics` (или другой роли).
2. `/builder` после CJM спрашивает «хочешь оставить фидбэк на агента?» — если да, вызывает `/fb agent:<role>`.

### Допустимые роли

| `role` | Что за агент |
|---|---|
| `research` | Research Agent — задавал брифинг-вопросы, формировал `researchOutput` |
| `analytics` | Аналитик — оценивал задачу с точки зрения метрик |
| `product` | Продакт-менеджер — расставлял приоритеты, искал ограничения |
| `experience` | Агент опыта — искал похожие кейсы зарубежных компаний |
| `implementer` | Figma Implementer — рисовал макет (обычно фидбэк по нему уже покрыт pulse в Шаге 8, но можно отдельно) |

Если в аргументе только `agent` (без роли) — спроси:

> «На какого агента хочешь оставить фидбэк? Research, Analytics, Product, Experience или Implementer?»

При неизвестной роли — мягко переспроси один раз. Если опять непонятно — используй `feedback:ux` (общий бакет) вместо agent-feedback.

### Шаг A1 — Собрать оценку

Задай **два коротких вопроса** в стиле Котика-Ботика:

> «Как тебе работа агента {role}? Что зашло, что нет — расскажи, что вспомнишь.»

Прими свободный текст. Потом второй вопрос:

> «Если бы ты могла что-то поменять в работе этого агента — что бы это было?»

Прими свободный текст. Оба ответа могут быть пустыми / «—» / «всё ок» — это нормально.

### Шаг A2 — Tone-классификация

Простая rule-based по ключевым словам:

| Сигналы в ответах | `agent_mood` |
|---|---|
| «плохо», «не зашло», «лишний», «глупо», «странно», «непонятно», «много вопросов», «слишком долго» | `negative` |
| «хорошо», «зашло», «помог», «полезно», «быстро», «✓» | `positive` |
| И те и другие — `mixed`. Пустые оба — `neutral`. |  |

### Шаг A3 — Собрать контекст автоматически

Не задавай эти вопросы дизайнеру:

- **Этап `/builder`**, на котором агент сработал (из истории сессии).
- **session_id** — если builder в активной сессии (`_session.session_id` уже сгенерирован).
- **HEAD:** `git rev-parse --short HEAD`.
- **Время:** ISO timestamp.

### Шаг A4 — Создать issue

Вызови `mcp__github__issue_write`:

```
operation: "create"
owner: "kotik-botik"
repo: "kotik-botik"
title: "[agent-fb] <role> · <session_id-короткий или date>"
labels: ["designer-feedback", "agent:<role>"]
body: см. ниже
```

**Body:**

```markdown
## Агент

{role}

## Что зашло, что нет

<первый ответ дизайнера или «—»>

## Что поменять

<второй ответ дизайнера или «—»>

## Контекст

- Тон ответа: <negative/positive/mixed/neutral>
- session_id: <если есть, иначе «—»>
- Этап /builder: <шаг>
- HEAD: <короткий хеш>
- Время: <ISO>
```

### Шаг A5 — Отчитаться

После успешного создания:

> «Зафиксировано — Настя посмотрит. Спасибо, это правда помогает 🧡»

При ошибке (нет прав / MCP недоступен) — fallback такой же, как в Шаге 5: показать markdown-блок, попросить отправить Насте.

### Если в активном /builder

Если фидбэк собран по ходу `/builder` (через шаг расширений), не выходи из builder — после Шага A5 продолжай с того места, где был builder. Все ответы дизайнера также записываются в `_session.agent_feedback` массив в формате `{ role, mood, note_what: "...", note_change: "..." }`, чтобы попасть в финальный telemetry issue.
