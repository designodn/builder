# /changelog

Скилл для обновления `CHANGELOG.md` и для пересказа последних изменений в режиме «для дизайнера» или «для разработчика».

## Identity-check (только для мутирующего режима)

Режим `/changelog` без аргументов **мутирует** `CHANGELOG.md`. Первым шагом вызови `mcp__github__get_me`:

- Если `login != "starkhoney"` — **тихо выйди**, ничего не пиши и не комментируй. Дизайнерская сессия не должна попадать в этот режим (GitHub Read-роль не пропустит push, но защита на уровне скилла лучше отказывает сразу).
- Если `login == "starkhoney"` — продолжай.

Режимы `/changelog designer` и `/changelog developer` — read-only, identity-check **не нужен** (доступны всем). Если пользователь не указал аргумент — это попытка мутации, identity-check обязателен.

## Автоматика

`CHANGELOG.md` обновляется **каждый день в 05:00 МСК** через GitHub Actions
(`.github/workflows/changelog.yml`). Воркфлоу пишет коммиты только за вчерашний день и пропускает технические (`chore:`, `wip`, `fixup`, merge-коммиты, повторные «update changelog»).

Если за день нет функциональных коммитов — запись не пишется.

> GitHub Actions cron работает под `github-actions[bot]` — он не идёт через identity-check скилла, у него собственная защита через workflow permissions. Identity-check выше касается только **ручного** запуска скилла из Claude Code сессии.

## Режимы запуска

| Команда | Что делает |
|---|---|
| `/changelog` | Если запустила Настя вручную — выполнить ту же логику, что Action: записать новый блок `[Unreleased — вчера]` в `CHANGELOG.md`. |
| `/changelog designer` | Показать **дизайнеру** упрощённое описание последних изменений (без хэшей, без префиксов `feat/fix`, без componentKey). Не пишет в файл. |
| `/changelog developer` | Показать **разработчику** детальное описание (с разделами, ссылками на файлы, упоминанием API/типов). Не пишет в файл. |

`designer` и `developer` — read-only режимы: они только пересказывают содержимое `CHANGELOG.md` (или последних коммитов, если в чейнджлоге ничего нет за нужный период) под нужную аудиторию.

## /changelog designer

Цель: дизайнер хочет понять, что нового в инструменте, но без техносленга.

1. Прочитай последний блок `## [Unreleased — YYYY-MM-DD]` из `CHANGELOG.md`. Если блока нет — возьми коммиты за последние 7 дней.
2. Перепиши каждый пункт **простым языком**, ориентируясь на сценарий дизайнера:
   - Не упоминай `componentKey`, `figmaPropName`, `assetType`, JSON-структуры, файлы агентов.
   - Заменяй технические термины: «registry» → «реестр компонентов», «component_set» → «набор вариантов компонента» и т.п.
   - Пропускай чисто-внутренние правки (рефакторинг, типизация, CI), оставляй только то, что меняет поведение Builder'а или дизайн-системы.
3. Сгруппируй по темам, понятным дизайнеру:
   - **Что нового в Builder** (изменения пайплайна `/builder`)
   - **Дизайн-система** (новые компоненты в `rules/`, обновлённые правила)
   - **Исправлено** (баги, которые мешали работать)

Формат ответа:

```
## Что обновилось (для дизайнера)

### Что нового в Builder
— Builder теперь сам различает обычные компоненты и наборы вариантов — стало меньше ошибок при импорте
— Спрашивать про экспертов теперь можно несколько раз подряд

### Дизайн-система
— В правилах появилось разделение на секции — Builder читает только нужные

### Исправлено
— Падения при импорте `header 1.1`, `inputText 1.0` и `button 1.1`
```

## /changelog developer

Цель: разработчик хочет понять, что менялось технически, для ревью или дебага.

1. Прочитай последний блок `[Unreleased — YYYY-MM-DD]` из `CHANGELOG.md`. Если блока нет — возьми коммиты за последние 7 дней (`git log --oneline --since="7 days ago"`).
2. Сохрани технические детали:
   - Conventional-commits-префиксы (`feat:`, `fix:`, `perf:`, `refactor:`)
   - Затронутые файлы (`agents/...`, `rules/...`, `.claude/commands/...`)
   - Типы / API / поведение
3. Сгруппируй по разделам:
   - **Агенты** (изменения в `src/agents/` и `agents/`)
   - **Реестр и схема** (`registry/`, `agents/shared/types.ts`)
   - **Скиллы** (`.claude/commands/`)
   - **Воркфлоу / CI** (`.github/`)
   - **Документация** (`docs/`, `rules/`, `CLAUDE.md`)

Формат ответа:

```
## Изменения (для разработчика)

### Агенты
- `agents/component-catalog/src/index.ts`: пишет `assetType` в `components.json` и в `registry/index.json`
- `src/agents/figma-implementer/...`: gate-чтения `rules.md` убраны, принимает план шага 6 как контекст

### Реестр и схема
- `CatalogComponent.assetType?: "component" | "component_set"` в `agents/shared/types.ts`
- `registry/index.json` — компактный индекс name → {lib, key, assetType}

### Скиллы
- `/builder`: gate шага 6 теперь читает только нужные секции `rules/components/*` и `registry/index.json`
- `/syncKeys`: push в main только по явному запросу

### CI
- `changelog.yml`: cron 02:00 UTC (= 05:00 МСК); пишет только вчерашние коммиты; идемпотентен по дате
```

## /changelog (запись новой версии вручную)

Используй когда Action упал или нужно поправить запись.

### 1. Собери коммиты

```bash
git log --oneline --no-merges --since="<дата последней записи>"
```

### 2. Сгруппируй

| Раздел | Что туда идёт |
|---|---|
| **Агенты** | Изменения в `src/agents/`, `agents/`, новые AGENT.md, изменения пайплайна |
| **Компоненты** | Новые/обновлённые записи в `rules/` и `registry/` |
| **Добавлено** | Всё остальное новое |
| **Изменено** | Изменения существующего поведения |
| **Исправлено** | Баги, некорректные данные |
| **Удалено** | Удалённые файлы/функции |

Не включай `chore:`, `wip`, `merge`-коммиты.

### 3. Запиши в CHANGELOG.md

Вставь новый блок **между `## [Unreleased]` и предыдущей версией**:

```markdown
## [X.Y.Z] — YYYY-MM-DD

### Агенты
- ...

### Компоненты
- ...
```

Секции без изменений — пропускай.

### 4. Закоммить (без push без явного запроса)

```bash
git add CHANGELOG.md
git commit -m "chore: update CHANGELOG for vX.Y.Z"
```

## Формат версии

SemVer:
- **MAJOR** — сломана обратная совместимость пайплайна
- **MINOR** — новый агент, новый компонент в `rules/`, новый своп-слот
- **PATCH** — исправление ключей, текстовые правки, баги
