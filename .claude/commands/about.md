**Доступен всем** — проверка личности не требуется.

## Алгоритм

1. Прочитай:
   - `.claude/commands/` — список скиллов (без `changelog.md` и `test.md` — это служебные).
   - `.claude/agents/` — sub-agents (включая экспертов Шага 4 — `analytics`/`product`/`experience` — и `cjm` Шага 5; раньше жили как `.claude/commands/extensions/*.md`, теперь source-of-truth там же в `agents/`).
   - `agents/*/` — агенты пайплайна.
   - `registry/libraries.json` (манифест: `id`, `name`, `enabled`).
   - `registry/index.json` (derived cache из rules: `components`, `libraries`).
   - **Самый свежий** `docs/SPRINT_*.md` (по дате в имени файла) — оттуда вытащи:
     - Даты спринта.
     - Верхнеуровневую цель каждой недели (1–2 предложения, своими словами, без жаргона: «Builder», «MCP», «placeholderHits» расшифровывай).
     - Топ-3 этапа каждой недели. Перепиши их в одно короткое предложение каждое — не копируй технические заголовки вроде «Этап 1.4 — Расширить покрытие правилами с 24.8% до ≥60%», превращай в «Покрыть правилами не 22%, а 60% компонентов».
2. Метрики проекта (один проход, без сети):
   - **Библиотек** = `len(libraries.json)`; **активных** = `sum(enabled == true)`; **в indexе** = `Object.keys(index.libraries).length` из `registry/index.json` (только enabled non-variables-only).
   - **Компонентов** = `Object.keys(index.components).length` из `registry/index.json`.
   - **Последний sync реестра** = `git log -1 --format=%cI registry/index.json`. Если пусто (shallow clone, tarball-скачка, файл не в истории) — fallback на `stat -c %y registry/index.json` или `fs.statSync('registry/index.json').mtime`. **Нормализуй вывод к ISO-8601** (`YYYY-MM-DDTHH:mm:ss±HH:MM`): `git log %cI` уже ISO, `stat -c %y` даёт `YYYY-MM-DD HH:MM:SS.NNNN +ZZZZ` (преобразуй), `mtime` — epoch (ms) → `new Date(mtime).toISOString()`. Если оба пусты — выводи `—`.
   - **Скиллов** = `.md` в `.claude/commands/` без `changelog.md`/`test.md`; **sub-agent'ов** = `.md` в `.claude/agents/`.
   - **Агентов** = каталоги первого уровня в `agents/`.
3. Метрики качества (из тестов):
   - Запусти `node tests/scripts/static-metrics.js` — берёт:
     - `rulesCoveragePct` — % компонентов реестра, покрытых файлом правил в `rules/components/`.
     - `propsDescribedCoveragePct` — % компонентов, у которых в правилах расписаны пропы.
     - `alwaysLoadedTokensEst` — оценка постоянно подгружаемого контекста.
   - Прочитай **последние 10 записей** из `tests/metrics.jsonl` с `mode: "full"` (`grep '"mode":"full"' tests/metrics.jsonl | tail -10`). Метрики шумные из-за нестабильности скрипта, поэтому считаем **медианы**, а не абсолютные значения:
     - Раздели выборку пополам: **«было»** = первая половина (старые прогоны), **«стало»** = вторая половина (свежие). При 10 записях — по 5 в каждой; при нечётном N средний прогон отбрасывается.
     - Для каждой метрики посчитай `median(было)` и `median(стало)`, и дельту `Δ = median(стало) − median(было)`.
     - Метрики: `placeholderHits`, `placeholderSignal` (тренд ↓ хорошо); `rulesCoveragePct`, `propsDescribedCoveragePct` (тренд ↑ хорошо).
     - Дата самого раннего и самого позднего прогона в выборке — границы окна.
   - Сопоставь с целями спринта: `rulesCoveragePct` → ≥80% (этап 1.4); ошибки → 0; `tokenCoverage` → 1.0.
   - Если записей `mode:"full"` меньше 4 — медианы не считаем, выводи прочерк и одну строку «недостаточно данных для динамики». Если ровно 4–9 — дели как можешь (по floor(N/2)) и укажи реальный N в заголовке. Если совсем нет — `—`.
   - Если в одной из половин все значения по метрике отсутствуют (метрика появилась в логах позже) — пиши `— (не писалась)` в этой половине и не считай Δ. Не подменяй пропуск нулём.
4. Собери ответ по шаблону ниже. Все числа — из файлов, не из памяти.
5. Не упоминай внутренние проверки доступа, режимы прав, разделение пользователей.
6. Не показывай дизайнеру технические детали реестра (`componentKey`, `assetType`, `keysHash`).

## Что это

Дизайнер пишет в чат на русском «собери экран оплаты с тремя способами и кнопкой подтверждения» — и в Figma появляется готовый макет, собранный из настоящих компонентов нашей дизайн-системы (а не нарисованных «с нуля»). Под капотом — пайплайн из AI-агентов, который ведёт дизайнера от текстового описания флоу до отрисованных фреймов, спрашивая апрув на каждом важном шаге.

### Что такое Builder

**Builder** — главный AI-агент проекта (`agents/builder/`). Он получает на вход:
- промт дизайнера («сделай форму регистрации с email и паролем»),
- каталог всех компонентов ДС из `registry/` (<всего компонентов> в <всего библиотек> библиотеках — числа подставляешь из метрик ниже),
- правила использования из `rules/components/*.rule.json` (как собирать `uniCell`, что подставить в `header`, какие пропы у `inputText`).

И выдаёт `layout.json` — дерево компонентов с расставленными вариантами и контентом. Дальше этот JSON отрисовывает Figma Implementer через MCP. Без апрува дизайнера Builder ничего не пишет на диск и в Figma не идёт.

### Пайплайн

`Research → Text Layout → JSON Layout → Builder → Figma Implementer` — пять шагов с апрувом дизайнера между каждым. Research задаёт уточняющие вопросы и собирает референсы, Text Layout рисует текстовый каркас экранов, JSON Layout превращает каркас в дерево компонентов ДС, Builder подбирает варианты и контент, Implementer отрисовывает в Figma.

### Неделя 1 (<даты>) — стабильная Figma-генерация

**Цель:** любой компонент из реестра можно использовать в макете, и он отрисуется правильно — без видимых поломок и без «silent failure» (когда компонент вставился, но в нём остался дефолтный текст «Title» вместо реального).

### Динамика по последним <N> прогонам `/test --full` — медианы первой и второй половины (<первый ts> → <последний ts>)
| Метрика | Было (медиана) | Стало (медиана) | Δ | Цель |
|---|---|---|---|---|
| Покрытие правилами, % | <rc_was> | <rc_now> | <rc_delta> <↑/↓> | ≥80% |
| Компонентов с пропами, % | <pc_was> | <pc_now> | <pc_delta> <↑/↓> | растёт |
| Placeholder hits | <ph_was> | <ph_now> | <ph_delta> <↓/↑> | 0 |
| Placeholder signal | <ps_was> | <ps_now> | <ps_delta> <↓/↑> | → 0 |

Стрелки выбирай по «хорошему» направлению: ↓ для ошибок (`placeholder*`), ↑ для покрытия (`rulesCoveragePct`, `propsDescribedCoveragePct`). `Δ` — со знаком (`+`/`−`). Если медианы равны — `0` без стрелки. В подписи под таблицей укажи, что окно разбито пополам и сравниваются медианы — чтобы сгладить шум одиночных прогонов.

**Расшифровка метрик** (выводи короткими буллетами под таблицей динамики):

- **Покрытие компонентов правилами, %** — доля компонентов реестра, у которых есть файл правил в `rules/components/`. Чем выше, тем меньше Builder работает «на ощупь» и тем стабильнее генерация. Цель спринта — ≥80%.
- **Компонентов с описанными пропами, %** — доля компонентов, у которых в правиле явно расписаны пропы и preferred values. Без этого Builder не знает, какие варианты применять — фолбэк на дефолт.
- **Always-loaded токенов контекста** — оценка постоянно подгружаемого Claude'у контекста (rules + `registry/index.json`). Чем меньше — тем дешевле каждый вызов и тем больше места под задачу.
- **Placeholder hits** — сколько раз в собранных макетах остался дефолтный контент компонента (например, текст «Title» в header) вместо реального. Прямой показатель silent-ошибок генерации. Цель — 0.
- **Placeholder signal** — суммарный «вес» placeholder-хитов с учётом критичности (заголовок весит больше, чем мелкий subtitle). Помогает увидеть прогресс, когда `placeholderHits` уже близок к 0, но качество ещё проседает. Цель — → 0.

Краткий вывод 1–2 предложения: ключевые победы (↓ ошибки / ↑ покрытие) и где просели. Полная история — `tests/metrics.jsonl`.
