## Тестовая инфраструктура (день 1–2, фундамент для всего остального)

Принцип: максимум автоматизации. Человеческие гейты — только семантические решения и финальный апрув PR. Все механические правки коммитятся атомарно, без вопросов.

### Принципы оптимизации токенов

Каждый шаг обязан спрашивать «есть ли уже локальные данные?» перед вызовом Figma MCP:

1. **Lazy MCP** — сначала читаем `inspected-props.json`, `components.json`, `_index.json`. Figma MCP вызывается только если локальных данных нет или они устарели (>24ч для baseline).
2. **Microtest на дефолтном варианте** — первый проход только для default-варианта компонента. Полная матрица строится только при прохождении дефолта (иначе базовая поломка, незачем гонять все варианты).
3. **Scoped /syncKeys** запускается только когда preferred values отсутствуют среди уже спаршенных. Не как дефолтный первый шаг.
4. **Кэш в сессии** — `inspected-props.json` читается один раз в начале heal-сессии, далее из памяти. Не перечитывать перед каждым компонентом.
5. **Стоп по первой критичной ошибке** — если `instanceCreated=false`, дальнейшие 6 ассертов не запускаются (компонент сломан на уровне ключа).

### T-0 — Матричный health-check (день 1, ~3ч)
**Файлы:** `tests/scripts/health-check.ts`, `tests/health-baseline.json`

Скрипт обходит весь `registry/index.json`:
1. **Pre-check**: если `health-baseline.json` существует и младше 24ч — пропустить, использовать кэш.
2. Для каждого компонента строит матрицу вариаций: сначала default-вариант, при успехе — остальные (потолок 12 наиболее показательных).
3. Прогон диагностики: `instanceCreated`, `variantApplied`, `defaultsAcceptable`, `swapsResolve`.
4. Сохраняет baseline: «150 компонентов × M вариаций → таблица статусов».

Запускается перед любым `/syncKeys` и расширением правил. Это диагностический фундамент.

### T-loop — Auto-heal loop (день 1–2, ~4ч)
**Файлы:** `tests/scripts/heal.ts`, `tests/heal-log.jsonl`

Универсальный цикл для одного компонента:
```
preflight: check local data completeness (inspected-props, _index, rule file)
  → escalate missing data sub-skills BEFORE any microtest

for attempt in 1..N (default N=5):
  result = microtest(component, variant='default')   # только дефолт-вариант
  if result.pass:
    if firstAttempt: run full matrix (all variants, max 12)
    break ✅
  diagnosis = classify(result.issues)
  if diagnosis.fixable_by_agent:
    patch = generatePatch(diagnosis)        # rule edit / _index.json / helper
    selfRegressionCheck(patch, sample=5)    # 5 случайных компонентов не сломались?
    if regression: rollback, mark 'stuck'
    else: applyPatch + autoCommit
    continue
  else:
    mark 'needs_human', break
```

Каждая итерация пишет строку в `heal-log.jsonl` (компонент, попытка, диагноз, patch-summary, verdict).

### Pre-flight data completeness check

До microtest heal проверяет наличие локальных данных и вызывает нужный sub-skill:

| Что отсутствует | Sub-skill | Когда |
|---|---|---|
| Нет записи в `inspected-props.json` | `rulesEnrich --stub` | Нет данных о пропах |
| Нет preferred values в INSTANCE_SWAP | `/syncKeys --scoped --page=X` | Только если пусто в уже спаршенных данных |
| Нет файла правил | `rulesEnrich --stub` | Генерирует скелет из `_TEMPLATE.md` |
| Нет записи в `_index.json` | Авто-добавление скелета | tier=`noRule`, без вызова Figma |

### /syncKeys — режимы

| Режим | Команда | Когда |
|---|---|---|
| Стандартный | `/syncKeys` | Полный ресканирование всех библиотек |
| Scoped | `/syncKeys --scoped --page=X` | Ищет preferred values только на одной странице, не только в Actual-секции. Используется heal автоматически. |
| Rescan | `/syncKeys --rescan --component=X` | Перепарсивает один компонент полностью |

**Вспомогательный реестр.** Компоненты, найденные вне секции Actual через `--scoped`, записываются в **отдельный файл**: `registry/libraries/<lib>/components-auxiliary.json`. Они никогда не попадают в основной `registry/index.json` и не читаются Builder'ом по умолчанию. Heal использует их только для разрешения конкретного INSTANCE_SWAP preferred value того компонента, на котором застрял.

Структура:
```json
// registry/libraries/buttons-tabs-chips/components-auxiliary.json
{
  "chipsRow 1.0 tight": {
    "key": "6b732dedd10b2d7b401fb4c571b89b4e4a70054d",
    "foundInPage": "Chips",
    "foundInSection": "Examples",
    "resolvedAt": "2026-05-14T10:22:00Z"
  }
}
```

### `/healSweep` — оркестратор (день 3, ~3ч)
**Файлы:** `.claude/commands/healSweep.md`, `agents/healSweep/src/`

**Как вызывать:**
```

/healSweep --scope=all
/healSweep --scope=buttons-tabs-chips   # конкретная библиотека

   ```

   ```
   ⚠ Needs human: 6 components — см. таблицу
   ❌ Stuck after 5 iter: 2 components — см. диагнозы
   ```

Доступ — только Настя.

### Классификатор авто-фиксов

| Класс проблемы | Patch |
|---|---|
| Wrapper-инстанс с дефолтным контентом | Добавить `requiredSwap` в `_index.json` |
| TEXT с placeholder | Override через `findAll` в правиле/helper |
| Не описан variant | Догенерить таблицу variant из `components.json` |
| INSTANCE_SWAP без preferred value | Подтянуть из реестра / auxiliary |
| `componentWithoutRules` | Сгенерить stub-правило по `_TEMPLATE.md` |
| Имя пропа с `#id` не совпадает | Нормализовать в helper |

Если диагноз не попадает в классификатор → `needs_human`.

### Self-regression check

Перед коммитом patch'а — re-run microtest на 5 случайных **других** компонентах (кэш baseline — без новых Figma MCP вызовов). Если хоть один деградировал → patch отбрасывается, целевой компонент помечается `stuck` без побочного ущерба.

### Регресс-гейт (сквозной)

После каждого коммита (включая auto-heal):
- Сравнение последней строки `metrics.jsonl` с предыдущей зелёной.
- Алерты: `placeholderHits` ↑, `unswappedSlots` ↑, `buildSampleTokensIn` > 10000.

Если триггер — последний коммит автоматически revert'ится, в `heal-log` пишется причина.

## Тоггл `nastya_approved` и flow гипотез

### Проблема

Heal может заполнить правила предположениями (AI-гипотезами) — но эти гипотезы не проверены. Компоненты с непроверенными правилами не должны учитываться в метрике `rulesCoverage%`.

### Поле `nastya_approved` в `_index.json`

```json
// rules/components/_index.json — запись компонента
{
  "chipsView": {
    "tier": "simple-swap",
    "nastya_approved": false,
    "requiredSwap": { "prop": "swap#7472:0", "preferredKey": "..." },
    ...
  }
}
```

- `false` (дефолт) — компонент имеет правила, но не проверен Настей. Не учитывается в `rulesCoverage%`.
- `true` — правила проверены и одобрены. Учитывается в метрике.

Метрика: `rulesCoverage% = approved / total`.

### Скилл `/rulesEnrich --hypothesize <name>`

Заполняет правило AI-гипотезами и выводит на апрув:

1. Читает `inspected-props.json` для компонента (пропы, типы, preferred values).
2. Для каждого пропа генерирует гипотезу использования: «скорее всего `paddings=true` нужен когда компонент располагается на краю экрана без отступов у родителя».
3. Записывает гипотезы в правило как `🤖 TODO: <гипотеза>`.
4. Выводит Насте серию вопросов с вариантами — по одному вопросу на каждую неочевидную пропу:
   ```
   Для компонента chipsView, проп `paddings`:
   - Нужен, когда компонент у края экрана без внешних отступов (предположение)
   - Нужен всегда, кроме случаев когда родитель уже задаёт padding
   - Другое (введи описание)
   ```
5. По ответам Насти обновляет файл правила (заменяет `🤖 TODO` на финальный текст).
6. После апрува всех пропов — ставит `"nastya_approved": true` в `_index.json`.

Heal запускает `--hypothesize` как последний шаг для компонентов в статусе `needs_human` (когда patch не нашёлся, но данных достаточно для гипотез).

## Неделя 2 (18.05–25.05): сайт-плейграунд ДС + рендер прототипов

### Этап 2.1 — Импорт индекса Storybook (день 6, ~2ч)
**Файлы:** `scripts/extract-storybook.ts` (новый), `tmp/storybook-index.json`

Storybook не нужен «по сети» — Claude Code работает на машине пользователя и читает файлы напрямую через Read/Glob.

**Вариант A (основной): локальный репо со stories.** Пользователь даёт путь к репозиторию ДС. Скрипт:
1. Glob по `**/*.stories.{ts,tsx,mdx}`.
2. Парсит каждый файл: `title` из default export, `component`, импорт-путь (`from '...'`), `argTypes`, имена stories.
3. Собирает в `tmp/storybook-index.json` единый формат: `{ stories: [{ id, title, name, importPath, componentName, argTypes }] }`.

**Вариант B (fallback): статический build.** Пользователь однажды запускает `npm run build-storybook`, отдаёт путь к `storybook-static/`. Скрипт читает `index.json` / `stories.json`.

В обоих случаях нужно: путь к репо/папке + npm-имя пакета ДС (`@your/ds`, для импортов в preview-app).

**Новая подпапка:** `playground/` (Next.js App Router, деплой Vercel)

Структура сайта:
- **`/`** — главная: счётчики «N компонентов / M прототипов», последние обновления.
- **`/components`** — галерея всех компонентов из `registry/index.json`. Карточки с превью.
- **`/components/[name]`** — страница компонента: рендер с дефолтными пропами, правая панель `<PropEditor>` (читает `componentProps` из `components.json`, выводит переключатели для variant, поля для текста, селекторы для INSTANCE_SWAP). Бейдж источника: ✅ Storybook / 🟡 Figma-gen / ⚪ Placeholder.
- **`/prototypes`** — список собранных флоу (из `prototypes/<slug>/prototype.json`).
- **`/prototypes/[slug]`** — кликабельный прототип: entry-экран + переходы по `onTap`.

Ядро — `<ComponentRenderer name={...} props={...}/>`:
1. Смотрит `registry/component-sources.json[name]`.
2. По `kind`:
   - `mapped` → `dynamic(() => import(source.package).then(m => m[source.import]))`
   - `figma-gen` → `dynamic(() => import(`@/generated/${name}`))`
   - `placeholder` → `<UnmappedComponent name={name}/>` (серая рамка).
3. Преобразует пропы через `source.propMap`, рендерит.

Прототип-страница — тот же renderer, обходит `NodeTree`, на `onTap` делает `router.push`.

Деплой: Vercel project, главная ветка автодеплоится, preview-deploy на PR. Один URL вида `figma-lib-playground.vercel.app` — стабильный, шарится на исследования.

## Агент-верификатор (Verifier)

### Проблема галлюцинаций в длинных задачах

При heal-sweep на 150 компонентов или при большом рефакторинге правил агент может:
- Утверждать, что ключ есть в `inspected-props.json`, не прочитав файл.
- Сообщать о «применённом патче», который на деле не был записан.
- Придумывать preferred values вместо того, чтобы брать из реестра.
- В конце sweep'а давать отчёт с числами, не совпадающими с реальным `heal-log.jsonl`.

### Решение: Verifier как co-pilot для длинных задач

**Принцип:** агент не доверяет своей памяти — он верифицирует факты через инструменты. Каждое утверждение о состоянии системы должно быть подкреплено Read/Bash в текущем ходу.

**Файл:** `.claude/commands/verifier.md` (новый, этап 1.2)

#### Чеклист верификатора перед каждым heal-шагом

| Утверждение | Как верифицировать |
|---|---|
| «Компонент X есть в реестре» | `grep -c "X" registry/index.json` |
| «Preferred value Y присутствует в inspected-props» | Read `tests/scripts/inspected-props.json`, поискать ключ |
| «Патч применён» | Read целевого файла правила после Edit, найти новую строку |
| «Коммит создан» | `git log --oneline -1` |
| «N компонентов исправлено» | `wc -l tests/heal-log.jsonl`, проверить verdict=fixed |

#### Режим работы во время /healSweep

Верификатор запускается как параллельный агент-наблюдатель:
1. Перед каждым batch'ем компонентов — читает `health-baseline.json`, запоминает числа.
2. После каждых 10 компонентов — читает `heal-log.jsonl`, сверяет реальные числа с утверждениями агента.
3. При расхождении > 2 компонентов — останавливает sweep, выводит таблицу расхождений Насте.
4. В финальном отчёте — все числа из файлов, не из памяти агента.

#### Правило для всех длинных скиллов (heal, syncKeys, genFromFigma)

**До начала работы** — явно прочитать и выписать стартовые значения ключевых метрик.  
**В середине** — checkpoint каждые ~10 операций: прочитать лог, обновить счётчики.  
**В конце** — отчёт строится исключительно из прочитанных файлов, не из внутреннего подсчёта.

#### Файлы ground-truth (никогда не доверяй памяти)

- `registry/index.json` — актуальный список компонентов
- `tests/scripts/inspected-props.json` — единственный источник preferred values
- `tests/heal-log.jsonl` — единственный источник статистики heal
- `tests/metrics.jsonl` — единственный источник метрик качества
- `rules/components/_index.json` — единственный источник tier/nastya_approved

| Риск | Влияние | Митигация |

## Источники React-кода для компонентов

Каждому Figma-компоненту присваивается один из четырёх `kind`, хранимых в `registry/component-sources.json`:

| Kind | Когда | Что рендерится в плейграунде |
|---|---|---|
| ✅ **mapped** | Есть в Storybook, замаплен через `/mapStorybook` | Импорт из npm-пакета DS пользователя |
| 🟡 **figma-gen** | В Storybook нет, но есть в Figma. Сгенерирован через `/genFromFigma` (`get_design_context`) | Файл в `playground/src/generated/<Name>.tsx`. Помечен `needsReview` до ручной вычитки |
| 🟠 **stub** | Редкое, ручной мини-каркас | `playground/src/stubs/<Name>.tsx` (опционально, если figma-gen не подошёл) |
| ⚪ **placeholder** | Совсем не получилось | `<UnmappedComponent name="X"/>` — серая рамка с подписью |

Приоритет на этапах 2.2 и 2.3 — довести максимум компонентов до `mapped` или `figma-gen`. Stub и placeholder — только если оба пути отвалились.
